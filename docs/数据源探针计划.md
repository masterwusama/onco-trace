# 数据源探针计划（P0）

这份文档管一件事：在建任何业务表之前，先实测每个维度到底有没有能自动落库的公开源、覆盖率多少。
产出物是 `source_probe_log` 表 + 一张 18 病 × 8 维的覆盖度矩阵，由它裁定 MVP 建哪些表。

数据全部来自公开源抓取，仓库里没有人工录入模块。人工判断只以两种形式存在：
仓库内的声明式配置（`etl/onco_etl/targets.py`、`sources.py`），以及对抽取草稿的一次目测抽查。

## 出口判据

判据是"建表之前必须实测到的东西"。实测列填的是探针跑出来的数，未跑的批次留空。

## 为什么 P0 不建业务表

`db/schema.sql` 只有 `source`、`dataset_release`、`source_probe_log`、`etl_job_log` 四张表。
症状维已经验证过一次"文档说有、实测没有"：HPO、Orphanet、NCIt 都声称提供疾病↔症状注释，
实测常见上皮癌拿不到可用行（证据见下节）。先按想象建 20 张表，探针回来发现喂不进数据，
就要再写一轮迁移改掉。覆盖度矩阵出来后再建表，一次建对。

## B2 实测结论：ID 主干与器官树

两维都过判据，但 ID 主干的枢纽换了源。

**器官树**——SEER 的 `sitetype.icdo3.d20220429.xlsx`（451875 字节 / 12496 行）一份文件同时供
anatomy 与 histology 两维：82 个 site recode（器官级分组）、332 个拓扑码、806 个去重形态学码。
18 病按 ICD-O-3 拓扑码段展开后与 site recode 求交，18/18 命中。
亚部位下钻（器官 → 具体部位）不用 NCIt 的 237 MiB 全量，改用 MONDO 里 145 个带 ICD-9 码的
亚部位 term，例如 `bronchus cancer`、`anal canal cancer`，粒度正好是页面要的那一层。

**ID 主干**——MONDO `releases/2026-09-01`（.obo 53134854 字节 / 63278 个 term）。
18 个疾病主条目的 MONDO ID 声明在 `etl/onco_etl/targets.py`，探针只做校验：
存在、非 obsolete、带齐必需的 xref。当前 18/18 通过。

主条目的 xref 完整度是这一批最重要的产出，它直接决定了谁是跨源枢纽：

| xref 前缀 | 18 病覆盖 | 缺口 | 用途 |
|---|---|---|---|
| NCIT | 18/18 | — | 跨源枢纽 |
| UMLS | 17/18 | uterus | 临床术语兜底 |
| MESH | 7/18 | 11 个常见上皮癌 | Europe PMC 文献检索的查准率 |
| EFO | 5/18 | 13 个 | Open Targets 对齐（GWAS 不受此限：它的 trait 词表本身以 MONDO 为键，见 B4） |

MONDO 带不动 MeSH 与 EFO，所以枢纽落在 NCIt 上（NCIt 自带 MeSH / ICD-O-3 / ICD-10 / EFO
交叉引用，一次补齐三个缺口），文献维另引 NLM 的 MeSH 描述符全量。两个源都已登记：

| code | 维 | 实测入口 | 体量 | 可达性 |
|---|---|---|---|---|
| `ncit` | identity, anatomy | `purl.obolibrary.org/obo/ncit.obo` → GitHub release asset | 248162694 字节 | 直连与代理都取到过（2026-09-08 这趟是 proxy） |
| `mesh` | identity, literature | `nlmpubs.nlm.nih.gov/projects/mesh/MESH_FILES/xmlmesh/desc2026.xml` | 312952703 字节 | direct |

两个都是年度/季度下一次的大文件，`upstream_version` 一律从文件头的 `data-version` 读，
不从 URL 读——NCIt 的 URL 里写的是 `latest`，MeSH 的 URL 里写的是年份，都会随发布漂移。

**症状与定位维**——MONDO 的 `disease_has_location`→UBERON 全库只有 775 行、
`disease_has_feature`→HP 只有 819 行，摊到 63278 个 term 上约 1%。这与下节症状维的结论一致：
结构化本体喂不出症状维，必须走 L3 抽取。

复现（离线重放已归档的文件，不重新下载）：

```powershell
ops\etl.ps1 probe --code icdo3_seer --code mondo --offline
ops\etl.ps1 probe-status
```

## B3 实测结论：统计层与生存率

四个源都跑完，各给一半：SEER 给了数但年龄粒度只有 8 档宽组，GBD 粒度够但数值全在登录门后，
GCO 门户下的两个数据库合起来正好补上缺口——Cancer Today 有中国国家级单点估计但没有年龄维，
Cancer Over Time 有 16 年 × 18 个 5 岁档但中国只有发病没有死亡。最后一条备选 WHO GHO 已排除：
年龄组与死因两维在维表里都齐，但带这两维的指标没有中国国家级行，有中国行的又都没有年龄维。

### SEER Cancer Stat Facts：达标，但年龄组不达标

`seer.cancer.gov/statfacts/html/<slug>.html`，18 病一页，共 1546896 字节，
`upstream_version` 取 18 页 `Last-Modified` 的最大值 `2026-04-22`（SEER 不给版本号，
statfacts 全站也没有发布日字段）。18 个 slug 与 target 的对应关系声明在探针里
（`lung→lungb`、`colorectum→colorect`、`uterus→corp` 等），逐个用 `<h1>` 标题核过语义。

**抓取契约**：每页 8 张 `class="scrapeTable"` 的表，但只有三种形状，且 `id="scrapeTable_NN"`
的编号与表在文档里的出现顺序不一致（实测 `lungb` 是 `_01 _02 _04 _05 _03 _07 _08 _06`）。
所以认领表格只能按文档顺序走，用最近的 `<strong>` 标题判定这张表填哪一维。
年度序列表是两行表头——第一行 4 个 metric 各 `colspan=2`，第二行 `Observed / Modeled Trend`；
种族费率表则根本没有 `<thead>`，6 行全是数据。按"第一行是表头"的通用假设切会两头错。

**四个 metric 的观测窗互不相同，这是这一批最该带走的数**：

| 年度序列表列 | 观测年数 | 区间 |
|---|---|---|
| Death Rate — U.S. / Observed | 50 | 1975–2024 |
| Rate of New Cases — SEER 8 / Observed | 49 | 1975–2023 |
| Rate of New Cases — SEER 12 / Observed | 32 | 1992–2023 |
| 5-Year Relative Survival — SEER 8 / Observed | 44 | **1975–2018** |
| 5-Year Relative Survival — SEER 8 / Modeled Trend | 49 | 1975–2023 |

18 页的 min 与 max 完全相等，说明这不是个别病缺数据，而是全站口径：**五年存活率的观测值停在一期，
2019–2023 只有模型趋势线**。所以 `stat_cohort` 必须把 Observed 与 Modeled Trend 落成两列，
前端画生存率曲线要标出哪一段是拟合——否则等于把外推当观测发布。

**判据改过一处**：第一版写的是"年龄分布双性别齐备"，18 页里判掉 5 页，而掉的恰好是乳腺、宫颈、
卵巢、子宫体、前列腺——性别特异癌在 SEER 只出一张表、页面上没有 `<h5>` 性别标签，性别只写在
口径行里（`All Races, Females`）。那是判据错不是数据缺。改为按 `targets.py` 新增的 `sex` 列校验，
并且口径行里出现对立性别时报 `conflict`（本仓库声明写错）而不是 `missing`（源缺），两者混报会引着人去查错的那一边。

**白血病无分期表**：`leuks.html` 全文没有 "5-Year Relative Survival by Stage at Diagnosis"，
只有 7 张 scrapeTable，生存率是一条 1975–2018 的时间序列。血液肿瘤本无实体瘤分期，
所以按页豁免而不是放宽判据——NHL 与骨髓瘤同为血液肿瘤却各有 Ann Arbor 分期表（5 档、4 档），
不能按 `category='heme'` 整类豁免。豁免名单是反着盯的：上游哪天补了表，探针会点名要求把它捡回来。
落地的处置即出口判据里那一行：白血病页展示全分期一个数并标口径。

**年龄组 8 档，未达 ≥10**：`<20, 20–34, 35–44, 45–54, 55–64, 65–74, 75–84, >84`。
画发病/死亡年龄分布够用，但做不了 5 岁组标化率。SEER*Explorer 底层是 2000 美国标准人口的
20 个 5 岁组，要更细得走它内部的 `render_region_*.php` JSON 接口——无公开文档、表单参数需逆向。
这一档缺口原本留给 GBD，GBD 实测之后不成立了（见下一节）。GCO 那两条匿名入口（再下一节）
已经把它补上：Cancer Over Time 给到 18 个 5 岁档 × 16 个年度，所以 5 岁组标化率这一项展示
保住，代价是它在中国是登记处抽样口径（5 个登记处、覆盖 60% 人口、只到 2017 年、只有发病没有
死亡），必须与 SEER 美国口径并排标而不是混算。WHO GHO 那条备选已跑完并排除（见其下小节，
实测 0/18），中国死亡年龄组这一半仍空，只剩 IHME 注册账号一条路，由 B7 一并裁定。
本批只上报不卡判据。

顺带量到种族/民族分层可用：6 组（All Races、Hispanic、Non-Hispanic AI/AN、API、Black、White），
发病与死亡各一套双性别表，MVP 不展示但落库时不必丢掉。

**未了的一件事**：`sources.py` 里给这个源写的 `legal_note` 要求"HTML 表结构改版频繁，
解析器必须留 fixture 回归"，但 `data/raw/` 整个在 `.gitignore` 里，18 页归档只存在于本机。
现在换一台机器 clone 下来，`--offline` 直接报"需要先有一份归档"，解析器没有任何回归保护。
不能一刀切要求所有源都检出归档——MONDO 那份 .obo 有 51 MB。所以这一条对 SEER（1.5 MB，
且三种表格形状里有两种是判据分支的边界：`leuks` 无分期表、`prost` 无性别标签）先欠着，
要么检 2~3 页代表页进仓库，要么在 B7 之前把 fixture 约定建起来。

复现：

```powershell
ops\etl.ps1 probe --code seer_statfacts --offline
ops\etl.ps1 probe-status
```

### GBD：设计口径全中，数值一条都不给

这一维的结论不是"GBD 能不能用"，而是"统计层缺一角还是缺整角"。所以判据拆两半分别裁定，
`verdict=blocked`、`diseases_covered=0`。

**词表这一半匿名可取**——`/sites/default/files/ihme_query_tool/IHME_GBD_2021_CODEBOOK.zip`，
127869 字节，里面一份横向词表 CSV 加四张层级 XLSX。注意版本是 2021：Results Tool 界面上的
Codebook 按钮到今天仍指向它，2023 版的词表跟着各 record 一起进了登录门。

| 词表维度 | 实测 | 判据 |
|---|---|---|
| 病因 | 18/18 病各有 L3 档，其下另带 13 个 L4 亚档：肝癌 6 档（肝炎 B/C、酒精、NASH、其他，加儿童肝母细胞瘤）、白血病 5 档按类型、NHL 2 档 | — |
| 地点 | 818 个，`China` = location_id 6（Level 3） | 中国 ✅ |
| 年度 | 1990–2021，32 个值 | ≥5 年 ✅ |
| 性别 | Male / Female / Both | 双性别 ✅ |
| 年龄组 | 155 档，其中 1 岁一档 94 个 | ≥10 档 ✅ |
| 度量 | Deaths / Incidence / Prevalence / YLDs 四个都在（词表共 21 个度量） | ✅ |

SEER 差的那一角，GBD 的设计里全有。

**数值这一半三条路都堵着**：

1. GHDX 的 22 个 GBD 2023 record 页面上，118 个文件行的 `<a href>` 一律被换成
   `/download-access/login`，而文件名、字节数、DOI、发布日照旧写在页面上（合计 6.3 GiB，
   最大单项 206 MB）。
2. 其中 2 个 record 整页要密码：**返回 HTTP 200 的 Protected Page**。这是本批最容易写错的一处——
   按状态码判可用，就会把它记成"页面正常、只是没有文件"，一个授权问题被写成源缺数据。
   认 `<title>` 才认得出来，离线重放时也只有标题可认。
3. Results Tool 自己的查询接口要 Azure AD B2C 换来的 token（`login.healthdata.org`，
   scope `https://ihmecsu.onmicrosoft.com/data-api/data.read`），打进前端的还是本地开发默认值
   `http://127.0.0.1:5000/protected-api`；界面前另有一层 Cloudflare 机器人校验。

**为什么词表全中仍记 0/18**：这一维要落库的是数，词表只证明"如果拿到数，粒度是对的"。
覆盖度矩阵要的是可用数据，不是设计意图——所以粒度那一半进 message 与 sample，
`diseases_covered` 留 0。

**要走通只剩注册 IHME 免费非商用账号这一条**，代价记三笔：license 是 CC BY-NC 4.0，
`commercial_use=False`；`source.auth` 从 none 变 register（登记表建表以来这一列第一次真被用上）；
token 换发叠加 Cloudflare，无人值守采集的失败模式会变多。这笔账留到 B7 判——统计层有 SEER
（美国口径）打底，中国口径那一半随后由 GCO 的两条匿名入口补上（国家级单点估计 + 登记处
年龄别逐年，见下一节），所以注册 IHME 换来的增量已经缩到"1990 年至今的完整年度序列与
1 岁一档"，不再是唯一的中国数来源，更可以从长计议。

复现（离线重放同一份归档会给出逐字相同的 118 个文件行与 6.3 GiB）：

```powershell
ops\etl.ps1 probe --code gbd_results
```

### GCO：真实入口没有门，但门户下是两个数据库

`gco.iarc.who.int/today/` 返回 200 的是 6 KB 的壳，数据在
`https://gco-api.iarc.fr/api/globocan/v3/<版本>/` 与
`https://gco-api.iarc.fr/api/overtime/v2/<版本>/` 两个 JSON API 上，
**全部匿名直连可取，没有 GBD 那道登录门**——可达性实测 direct/200，`source.auth` 仍是 none。

版本号不是常量也不是 URL 的一部分：`v3/[vdb]` 里的 `[vdb]` 是前端构建常量
（Today 的 bundle 里写着字面量 `data_version` 后跟一个四位年份，Over Time 的
`chunk-vendors.js` 里写着 `api/overtime/v2/22/`），两个探针都从 bundle 正则读，
换季版时不用改代码。

**一个门户两个数据库**，而且癌种码空间互不通用：

| | Cancer Today | Cancer Over Time |
|---|---|---|
| 是什么 | GLOBOCAN 国家级估算，一版一个年份 | 登记处汇编的逐年观测序列 |
| 中国 | country=156 | 同，但 `bool_national=False` |
| 年龄组 | **没有**（路径末段实测是癌种过滤器，`ages_specific=1` 无效） | 18 个 5 岁档 0-4…85+，另有 `unk` |
| 年度 | 单点（公开发布共 7 档：2012/2018/2020/2022 1.0·1.1·1.2/2024） | 2002–2017 共 16 年 |
| 肺 / 结直肠 / NHL / 骨髓瘤 | 15 / 41 / 34 / 35 | 11 / 106 / 26 / 27 |
| 中国发病 | 18/18 | 18/18 |
| 中国死亡 | 18/18 | **0/18**（`mortality=false`，`type=1` 实测回 0 行） |

`C88` 在 Today 归 Non-Hodgkin lymphoma(34)，在 Over Time 归 Multiple myeloma(27=「C88+C90」)，

## B4 实测结论：危险度（GBD CRA 这一半）

判据是每病 ≥3 个危险因素**带 PAF 或 OR + CI**。实测 `verdict=blocked`、**效应量 0/18**；
同一趟量到的关联骨架是 **10/18**——关联与效应量这两件事必须分开报，混在一起就成了
"GBD 危险因素可用 / 不可用"这种没用的话。GWAS Catalog 那一半见下一节，结论正好相反。

授权面逐个复核，结论与 gbd_results 同一道门但入口不同：

| vizhub GBD Compare 的面 | 实测 |
|---|---|
| `GET /api/config` | 200 匿名，内容只有版本面（`releaseText=GBD 2023`、`gbdYear=2023`、`copyYear=2025`） |
| `GET /api/metadata`、`/api/data`、`/api/hierarchy`、`/api/data/version` | 一律 **401** `Unauthorized.` |
| `GET /api/language`（对照） | 404 `Not found.` —— 所以那四个 401 是"路由在、要授权"，不是整站兜底 |

数值要走通只能注册 IHME 免费非商用账号（Azure AD B2C，scope `data-api/data.read`）。

匿名可取回的是 data guide 页挂着的 `IHME_GBD_2023_A2_RESULTS_BY_MEASURE_Y2025M10D23.XLSX`
（294 KB / 5 张表）：

| | 实测 |
|---|---|
| `Risk` 表 | 真数据 **2390 行** = 2390 个 cause×REI 对（217 个病因 × 88 个 REI）。openpyxl 的 `read_only` 报 8917 行，其中 6527 行整行空白——行数只按带真值的行登记，否则 `dataset_release` 会记下这份文件没有的规模 |
| 度量列 | `Deaths/YLLs/YLDs/DALYs` 四列的值只有 `X`（该组合有数）或空，**数值型列 0 个** → 能建关联、建不了 `paf` |

| REI 层级 | A2 里没有 parent/level 列，2023 版层级 record 页面上没有任何未登录文件链接 → 只能继续用 2021 codebook 的 `REI Hierarchy`。本版 88 个 REI 全部在 2021 表里找得到，两版之间没出现过重编号 |

聚合档必须剔，否则一个危险因素会被数成十几个（`Dietary` 与它下面十几个子档会同时出现在同一病的行里）。

`High fasting plasma glucose` 是二档却自带暴露与 PAF，按层数切会把达标病数从 10/18 误判成 7/18。

## B4 实测结论：危险度（GWAS Catalog 这一半）

同一道判据，跑的是匿名整包 `releases/2026/09/` 的 `…ontology-annotated-full.zip`
（2026-09-04 发布，73,489,749 B；里面那张关联表展开 740,716,183 B、1,192,032 行 / 38 列）。
实测 `verdict=partial`、**覆盖 14/18**。

这一半与 CRA 恰好互补，两半合起来才是危险度维的真实形状：

| | GBD CRA（A2 交叉表） | GWAS Catalog（全量关联） |
|---|---|---|
| 关联（病 × 因素） | ✅ 2390 个 cause×REI 对，骨架 10/18 | ✅ 主条目有行 16/18 |
| 效应量 | ❌ 度量列只有 `X` 标记 | ✅ `OR or BETA` 非空 84.3%，`95% CI (TEXT)` 含可解析区间 75.0% |
| 因素语义 | 可干预暴露（吸烟、BMI…） | 遗传位点，不是可干预暴露 |
| PAF | 无 | 无（全表 38 列没有一个归因分数列） |

四条口径，都会直接决定 P1 能不能自动落库：

1. **CI 非空 ≠ 有区间**。`95% CI (TEXT)` 非空 991,389 行（83.2%），其中 97,360 行（8.2%）
   根本没有区间，只有 `unit increase`(25,793)、`unit decrease`(24,474)、
   `z score increase`(9,888)、`[NR]`(5,005) 这类文字；真含 `[a-b]` 区间的是 894,029 行
   = 全表 75.0%。那 97,360 行里含 2 个畸形串（`[1.80-.5.00]`）按解析失败计——
   宁可不计数也不猜边界。所以"CI 填充率"只能按含可解析区间报。
2. **`OR or BETA` 是一列混装，符号不在这列里**。全表值 <0 的只有 6 行，
   方向写在 CI 文本的 `unit increase/decrease` 注记里——带这条注记的有 841,694 行，
   与含区间那批有重叠（主流形态就是 `[1.09-1.22] unit increase`，两个计数同时命中这一行），
   所以这两个数不能相加。
   OR 与 β 在区间同为正时形态分不开，`effect_kind` 只能整列留未判定，
   不许按"值 <1 就是保护性 OR"这种猜法。
3. **疾病侧以 MONDO 为键**。`MAPPED_TRAIT_URI` 的值就是
   `purl.obolibrary.org/obo/MONDO_0008903` 这种形态（24619 个 trait 档里 2129 个是 MONDO_），
   所以 B2 那个"EFO xref 只有 5/18"的缺口在这里不构成障碍——方向反过来，
   拿 targets 的 `mondo_id` 精确命中即可，不猜名字。
4. **`MAPPED_TRAIT_URI` 是多值列，分隔符实测是逗号不是分号**。96,520 行一行带 2~7 个档，
   因为 MR 研究把暴露档与疾病档并在同一行（`diet measurement, colorectal cancer`）。
   整格不拆开就取尾段，这 1,339 行会伪装成"这一病自己的一条遗传证据"，
   把膳食暴露的遗传工具变量当成结直肠癌的位点证据——16/18 与 14/18 两个数都会虚高。
   所以探针只把单档行算进命中，混档行按病进 `sample.main_multi_uri_rows`
   （结直肠 798、肺 116、卵巢 78、骨髓瘤 69…）。同一行里 `MAPPED_TRAIT` 与 URI 共用逗号、
   但两列拆出来的档数对不上的有 9,191 行（有的档名自己就带逗号），
   所以拆档只认 URI，label 只能当整串文本用。

覆盖度卡在**粒度**不在字段。按 targets 声明的主条目 URI、要求 ≥3 个带效应量与区间的独立位点，
只到 14/18，掉队的四病是：

| 病 | 主条目行 / 带效应量与区间的位点 | 同级候选档（行数） |
|---|---|---|
| breast_female | 0 / 0 | breast carcinoma 1832、breast cancer 319、ER-negative 84 |
| uterus | 0 / 0 | endometrial carcinoma 102、endometrial cancer 28、uterine carcinoma 5 |
| pancreas | 12 / 0 | exocrine pancreatic carcinoma 171、pancreatic IPMN 16 |
| esophagus | 7 / 1 | esophageal squamous cell carcinoma 50、carcinoma of esophagus 30、esophageal adenocarcinoma 25 |

把同级候选档并进来 18/18 都过 ≥3 位点，但那是**上界**，`diseases_covered` 仍记 14/18：
并档必须变成 targets 里逐病声明的 URI 列表（人工裁定），不能让归一化脚本按关键词并。
候选档里也确实混着必须踢掉的东西——`family history of breast cancer`（那是暴露不是结局）、
`breast benign neoplasm` 与 `uterine benign neoplasm`（良性）、`ovarian endometrioid adenocarcinoma`
（挂在子宫体候选档里，属跨病）。探针把逐病候选档连行数一起放进 `sample`，就是为了让这次
裁定不用再回源站。

落库含义：GWAS 只喂 `role='genetic'` 那一层，每条带 `OR/β` 与区间，`paf` 留 NULL、
`effect_kind` 留未判定。它补不上 CRA 缺的"可干预暴露 + 归因强度"，
所以危险度维在匿名侧仍然是**有清单、有遗传效应量、无归因强度**。

取数姿势：整包必须按 8 MB 分段 Range 续传。单条长连接实测在 53,767,694 B 处被断流，
而且以 HTTP 200 正常收尾——只看状态码会拿到一个残包，`zipfile` 报"不是 zip 文件"，
看着像源坏了。前缀采样也不行：关联表按录入年份排序，取前若干行会把填充率系统性量偏。

复现：

```powershell
ops\etl.ps1 probe --code gwas_catalog
ops\etl.ps1 probe --code gwas_catalog --offline   # 重放同一份归档，9 s
```

## B5 实测结论：研究层

判据那一行是三个源合起来判的：`每病在注册试验 >0、近 5 年文献 >0、OpenTargets 关联 ≥10`。
三列都 18/18，所以**前沿研究这一维进 MVP，不走"从 MVP 剔除"那条退路**。
最低的三个数离判据线都很远：在招试验最少 thyroid 292 项，近 5 年文献最少 uterus 10,366 篇，
关联靶点最少 breast_female 643 个（判据是 10）。

三个源给了三种疾病键，这是这一批真正的产出：

| | 疾病键 | 匿名可取回 | 匿名取不回 |
|---|---|---|---|
| ClinicalTrials v2 | 只能按声明查询词——`fields=` 白名单里没有可对齐的 MeSH ID | 命中数、状态分层、23 列协议字段 | 地理与性别/分期筛选 |
| Europe PMC | 同上——`MH:` 字段只覆盖全库 2.2%，当不了键 | 命中数、OA/IN_EPMC facet、记录级 flag、core 字段 | 数据发布日（只给搜索版本 6.9） |
| Open Targets | **MONDO ID 直接命中**（冒号换下划线） | 带分数的靶点清单、逐数据源分、在研药数 | 按名字换更宽的档——要人裁 |

四条口径会直接决定 P1 怎么写抓取脚本：

1. **CT 的引号会换检索模式**。裸写走 MeSH 概念映射，加引号走字面短语。同一病按同口径比，
   裸写主题词比整串加引号多 9,787 项（18 病合计），而声明的自由文本同义词又在主题词之上
   多并进来 2,823 项、13 病有增量（brain +1,021、liver +606）——**两个增益方向不同，省掉任一都数错**。
   但同义词绝不能裸写：8 个词裸写命中超过加引号的 2 倍（colorectum「colon cancer」8,256 对 2,273、
   cervix「cervical cancer」11,331 对 2,538、breast_female「female breast carcinoma」4,182 对 78），
   因为非主题词裸写退化成词级匹配，会把别的癌种灌进来。所以主查询固定为
   「第一项裸写 OR 其余加引号」，逐词裸/引比值进 `sample` 当词表体检。
   计数有机制：`countTotal=true` 让顶层多一个 `totalCount`，实测与逐页数出的行数完全相等——
   这一支第一版不知道它，按 pageSize=1000 翻页数了约 160 个请求 467 s（那行裁定留在
   `source_probe_log` 里当运行史，dataset_code=`studies-query-cond`，已被取代）。
   在招可以问（`filter.overallStatus` 与 `query.cond` 同时生效），地理不能问
   （`filter.geo` 三种写法与 `aggFilters=geo:CHN` 都拒，900 条抽样 0 条中国大陆地点）。
2. **全文可得率是两个数，不是一句"可得率多少"**。facet 口径 OPEN_ACCESS 50.8%、IN_EPMC 56.5%，
   同一批查询的记录级抽样 900 条只有 31.7% `isOpenAccess`。差额是抽样构成造成的
   （抽到的源里 MED 845、PPR 47、PMC 8，而单病实测 MED 内部 OA 只有 24.0%、PMC 内部 81.8%）。
   **B6 判断 L3 能不能拿到正文要看 31.7% 这个数**，前端展示用 50.8%。
   年份过滤必须配 `lucene=true`——`PUB_YEAR:2021-2025` 那种连字符写法被静默忽略，
   回的是不加过滤的全库数，一个错字都不给；查询串一律交给 `urlencode` 生成，
   自己拼 `%20` 会量出不同的命中数（实测 20,275 对 3,474）。
3. **OT 的窄档问题是按病分布的，不是普遍现象**。`literatureOcurrences.count` 在层级上不单调：
   lung 自己 381,600 篇，比它的父节点（3,683 / 511 / 1,636）大两个量级——这类病不用管；
   但 breast_female 只有 88 篇而父节点 breast carcinoma 710,750 篇、pancreas 382 对
   父节点 166,685。**这一维要显示"这一病的研究热度"，这两个病就得按父节点或更宽的档重新声明**，
   探针不自己按名字换档（换了就破坏 `icd10` 语义对齐），交 B7 裁。
   取数姿势两处：疾病侧点查一次 18 病全中（`MONDO_0008903` 这种下划线形态），
   但 `associatedTargets` 之外一旦带上 `parents` 批量就 HTTP 408，只能 6 病一切；
   靶点清单带 `score` 与 `datasourceScores`（lung 前三：EGFR 0.901、KRAS 0.858、ERBB2 0.842）。
4. **整包不是"顺手就能下"的量级，而站点按点查用就够**。平台 26.06（发布 2026-06-23）的 `output/`
   是 56 个数据集 / 1,102 个 parquet 分片 / 58.5 GiB（最大 colocalisation 20,000 MB）。
   croissant 清单的 56 个 FileSet 目录名与 FTP 实到的 56 个完全一致（对账过），
   但它只给三个分发根、不给单文件大小，`distribution` 根条目里的 `sha256` 字段值是字面量
   `'sha256'` 占位——所以体量只能逐目录列，这一趟 57 个 LIST 请求。
   **`download_url` 回填的是那份 croissant 清单**，不是某个 parquet。

落库形状随之定了：`trial` 逐病按主查询分页取 23 列，`overall_status` 存原值 + 我们的三档映射
（在招 / 未招募但随访 / 已完成），"有没有中国参与"只能落 `locations.country` 数组再前端筛；
`literature` 按 pmid 建键（填充率 93.9%，DOI 98.6% 但只当可选链接），逐篇存 OA 与 IN_EPMC flag
而不是存一个库级率；靶点与药反查走 OT 的点查结果落关联表，`paf` 那类归因分数这里没有。

稀疏列按性质允许为空，不算未达标：23 个候选列实测过半有值的是 18 个，
`collaborators` / `location_countries` / `other_outcome` / `publications` / `why_stopped` 低是试验本身的性质。

给 B6 顺带一条负向证据：**OT 的 `phenotypes.count` 有 9 病是 0**（liver、breast_female、prostate、
thyroid、kidney、brain、uterus、leukemia、nhl），其余病也只有 2~8 条——靶点库的表型注释当不了症状维的源。

还有一件要人裁的：croissant 清单的 `license` 字段写的是 CC0，
而登记表里 OT 那一行写的是"平台 Apache 2.0，数据随上游"——**署名口径以清单为准还是以平台条款为准**，
探针不替它改，两句话现在都在库里。

复现：

```powershell
ops\etl.ps1 probe --code ctgov_v2      # 149 s，249 个请求
ops\etl.ps1 probe --code europepmc     # 183 s
ops\etl.ps1 probe --code opentargets   # GraphQL 点查 + FTP 逐目录列表
ops\etl.ps1 probe --code ctgov_v2 --offline
```

## 症状维的实测结论

这是全站最弱的一环，也是唯一需要 L3 抽取兜底的维度。

| 源 | 实测 |
|---|---|
| HPO `phenotype.hpoa`（v2026-09-02，35.8 MB / 252467 行 / 11598 病） | 第一列零个 MONDO ID；常见癌 3~9 行，且那些"症状"是肿瘤本身（`HP:0003002` Breast carcinoma、`HP:0006753` Neoplasm of the stomach），Frequency 全空。肺癌/胰腺癌/AML 作为条目 0 行 |
| Orphanet `en_product4.xml`（2026-07，45.7 MiB，CC BY 4.0） | 4357 病 / 116664 行，**每行都带六档频率带**（Very frequent 99-80% / Frequent 79-30% / Occasional 29-5% / Very rare <4-1% / Obligate / Excluded），可直接映射 `freq_band`。但只覆盖罕见病：肺/结直肠/前列腺/胃/宫颈/成人肝 0 命中；血液肿瘤可用（CML 11 条、滤泡淋巴瘤 17 条） |
| NCIt 26.02d（248 MB obo 全量扫） | `NCIT:C2926`（肺 NSCLC）零条 relationship；`Disease_May_Have_Finding` 在疾病段几乎不出现 → 不可用 |
| Monarch v3 API | 肺腺癌 0 条、胰腺腺癌 0 条；膀胱癌 8 条真可用（血尿/排尿困难/腹痛/高钙血症，带频率）；甲状腺癌 191 条是亚型上卷，精度差（混入"厚下唇""漏斗胸"） |
| HPO 遗留 `common_disease_annot.tar.gz`（2015 文本挖掘） | 原发性肝癌 111 行、结直肠 111、食管 81、胰腺 55，但 16495 条癌症行 Frequency 全空，58 个癌文件只有 1 行 `HP:0002664` Neoplasm；已被 HPO 主线弃用 → 只能当症状词表候选 |
| SymMap / NCI PDQ API | SymMap 域名已无法解析；PDQ 没有 JSON/XML 端点，只有 HTML |

结论：零抽取的话，症状维只对血液肿瘤与遗传性癌综合征成立。因此采用三级 pipeline，
L3 抽取是唯一的兜底，且必须带审阅状态落库。

## 三级抽取

| 级 | 含义 | 适用 |
|---|---|---|
| L1 | 码表/统计库直取，零歧义 | ICD-O-3、MONDO、GBD、SEER、GWAS Catalog、OpenTargets、ClinicalTrials、Europe PMC |
| L2 | 规则化 HTML 解析 | SEER Cancer Stat Facts 的统计表、WHO fact sheet |
| L3 | 一次性 LLM 抽取兜底 | PDQ/WHO 正文 → 症状与频率带 |

L3 落库时必带 `extract_method='llm_extract'`、`review_status='unreviewed'`、
`provenance='derived-from-PDQ-<rev>'`。自动作业之后只负责检测上游版本变化并重新出草稿，
不覆盖已确认行——判定依据是 `dataset_release.upstream_version`。

**L3 的质量怎么测**：`etl/probe/l3_symptom.py` 对 18 病各抽一次，
只写到 `data/exports/l3_symptom_draft_<code>.md`（不入库），每行带 `source_url` + 原文引句 +
中文症状名 + 频率带；对 5 个病做一次目测打分，结果记进 `source_probe_log.message`。
判定线：≥80% 是真症状（排除肿瘤同义复述、排除遗传综合征体征），且每病 ≥4 条。
不达线的病症状模块留空并显示"暂无可靠来源"，不硬凑。

## 候选源清单

`direct` = 本机直连可取；`proxy` = 直连失败、走 `.env` 里 `PROXY_URL` 才取到。
这个区分是必需的：scheduler 要无人值守跑，不能靠临时代理。

| `opentargets` | trial, literature | GraphQL 点查 + FTP 整包 56 数据集 / 1,102 分片 / 58.5 GiB | 平台 Apache 2.0，数据随上游（清单自己的 license 写 CC0，待裁） | direct（壳已拆：GraphQL 与 EBI FTP 都是真入口） |
| `who_factsheet` | narrative | HTML | CC BY-NC-SA 3.0 IGO，**禁商用** | direct |

壳类源要特别注意：返回 200 的是前端壳，不是数据，真实入口是各自的 API 或 FTP。
现在三个壳全部拆完了，答案两两不同。GCO 的壳背后是两份匿名可取的 JSON API，`download_url` 回填的就是
它们（上面 `globocan` 与 `gco_overtime` 两行，同一门户两个数据库）；GBD 的真实入口存在但排在
注册门后面，所以它的 `download_url` 回填的是那份词表 ZIP，不是数值。`gbd_cra` 回填的是挂 A2
附件的那页 guide（附件名带发布日，不能当入口，详见上节）。OpenTargets 的壳拆出两个真入口，
回填的是 EBI FTP 上那份 `croissant.json` 发布清单——它是唯一一份"一次请求说清这一版有什么"的东西，
56 个数据集与 58.5 GiB 的体量就是从它的 FileSet 逐目录列出来的（详见 B5 那节）。
**填了 `download_url` 不等于这一维通了**，
判据只认探针回来的 `verdict` 与 `diseases_covered`。

`gwas_catalog` 的真实入口是 `ftp.ebi.ac.uk/pub/databases/gwas/releases/<年>/<月>/` 下的
`gwas-catalog-associations_ontology-annotated-full.zip`，`latest/` 只是它的镜像，
所以 `upstream_version` 从日历目录读（实测 `2026-09`）、`release_date` 取这份包在 FTP 上的日期
（实测 2026-09-04），都不拼死。疾病侧对齐靠件内的 `MAPPED_TRAIT_URI`：这一列是混装的（24619 个 trait 档里 `MONDO_` 2129 个，
其余是 `EFO_`、`OBA_` 等），但癌种档正好落在 MONDO 上，所以拿 targets 的 `mondo_id`
直接命中就行，B2 的 EFO 缺口不影响这一路——不许按前缀假定整列同一种 ID。
旧的 `/gwas/api/search/downloads/full` 已 404 下线。

都只能靠 IHME 注册账号解开，所以这是 B7 的一个决定而不是两个：开账号就同时补两维，

剩下不确定性最高的是 B6——取决于抽取质量能不能过 80% 那条线。

## 三条红线

1. **授权**：`source.legal_note` 为空视为未通过 P0，`seed-sources` 会直接拒绝写入。
   NCCN、UpToDate、Cancer Research UK 条款禁止抓取，不列入候选。
   `gbd_*` 与 `who_factsheet` 是非商用许可，站点若要商用必须先换源。
2. **跨源冲突并存不覆盖**：SEER（美国）与中国国登的 5 年生存率能差三十个点。
   `stat_cohort` 的唯一键必须含 `source_id + dataset_code + 全部口径维度`，
   前端按口径并排展示，禁止任何"取平均"。
3. **`freq` 与 `freq_band` 分工**：公开资料绝大多数只给"常见/少见"，精确百分比极少。
   `freq decimal NULL` 允许大面积为空，`freq_band` 才是主字段；
   UI 上的症状频率用区间条而不是折线，避免把定性来源画成定量结论。
